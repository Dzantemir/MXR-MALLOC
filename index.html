Architecture

How the allocator thinks

Every request is filtered by capability bits. EXEC and pure 32BIT land in IRAM first (EXEC from start, 32BIT from end, reserve between them); only when IRAM is exhausted does the request fall through to DRAM regions, and — only if enabled — cross into another DRAM region as a last resort.

Descriptor format

Eight bytes per allocation

Each live block owns one 8-byte descriptor in a sorted table. Bit 31 of off_flags marks the arena; bit 31 of len_flags marks EXEC. Move the sliders — the bit pattern updates live.

off_flags — arena + offset (bytes)
len_flags — exec + length (bytes)

31-bit fields cover ~2 GB per arena — enough for any ESP8266 DRAM/IRAM configuration. Because DRAM descriptors always sort before IRAM ones, one binary search serves both arenas.

0x00001410
Resulting pointer
0x3FFE9410

Region configuration

Design your size classes

Regions are defined by lower boundaries only — "4,132,1024" — so gaps and overlaps are impossible by construction. The last region is always unlimited and absorbs leftover memory. This calculator runs the exact init logic.

Installation

Drop-in via linker --wrap

The original heap component stays in the build; every entry point is redirected at link time. Nothing in the SDK needs to be modified.

01

Copy the component

Place the component into your project tree.

shell
cp -r mxr_heap/ <your_project>/components/mxr_heap/
02

Configure

All parameters live under the MxR-malloc menu. Defaults are safe for most projects.

shell
idf.py menuconfig
# → MxR-malloc → regions, IRAM, search mode, wrap options
03

Full clean build

Always fullclean after changing MxR Kconfig options — stale sdkconfig values silently override new defaults.

shell
idf.py fullclean
idf.py build
04

Verify at boot

Call mxr_dump() once after startup and check the region table and IRAM status.

C
#include "mxr_malloc.h"
void app_main(void)
{
    mxr_dump();   /* regions, IRAM, descriptor table, stats */
}

In practice

/* DMA-safe buffer: always DRAM, never IRAM */

FAQ

Questions that actually come up

Why does esp_get_free_heap_size() differ from the original heap?
v2 routes MALLOC_CAP_32BIT to IRAM first, matching the original SDK. The numbers should now be close; remaining differences come from MxR's EXEC reserve and the descriptor-table cap. Compare apples to apples with heap_caps_get_dram_free_size() — it returns DRAM only in both implementations.
What happens when the descriptor table fills up?
malloc returns NULL even though memory is free — this is the one failure mode the original heap doesn't have. Watch alloc_fail_table_full and max_active_allocs in mxr_get_status(); raise CONFIG_MXR_MAX_DESC if you approach the cap. 256 covers typical WiFi + LWIP workloads.
What is cross-region fallback and why is it off by default?
When CONFIG_MXR_CROSS_REGION_FALLBACK=y, if a block's own size-class region and IRAM are both exhausted, the allocator tries other DRAM regions, picking the one with the smallest min_bytes. It's off by default because dropping a small block into a large-block region fragments it. v2 removed the CONFIG_MXR_CROSS_REGION_AFTER_IRAM toggle — order is now fixed: IRAM → DRAM → cross-region. Watch cross_region_allocs — if it grows, enlarge the own region's percent instead.
Can I keep CONFIG_HEAP_TRACING enabled?
No. The original tracing walks multi_heap structures that don't exist in MxR. Disable it — MxR emits a build warning if it's on. Same applies to heap poisoning.
Is MxR safe to call from ISRs?
No — same as the original heap. malloc/free must not be called from interrupt handlers.
Why aren't calloc/realloc in IRAM by default?
To keep the IRAM footprint small — only malloc/free are IRAM-resident by default. Enable CONFIG_MXR_IRAM_PATH_ALLOC_FAMILY to place calloc/zalloc/realloc in IRAM too (for code running during flash write/erase), then verify with idf.py size. The allocator is still not ISR-safe.
Why is DRAM aligned to 4 bytes instead of 1?
One unified descriptor format serves both arenas (IRAM is 4-byte-only hardware). The cost is at most ~3 bytes per block — roughly 50–1000 B across a busy system — in exchange for a 4-byte descriptor and identical handling of DRAM and IRAM.
What does realloc(ptr, 0) do?
By default it frees the block and returns NULL (glibc / ESP-IDF style), controlled by MXR_REALLOC_ZERO_FREES in the header. Set it to 0 to restore the allocate-minimal-block behavior.
What changed between v1 and v2?
v2 doubles the descriptor to 8 bytes (byte-granular offsets/lengths, ~2 GB max), routes MALLOC_CAP_32BIT to IRAM first (matching the original SDK), removes the bitmap search mode, adds configurable descriptor placement (DRAM/IRAM .text/IRAM .bss), adds compact type widths for ESP8266, and adds a selectable diagnostics verbosity. realloc(ptr, 0) now follows glibc/ESP-IDF semantics by default.
Where does the descriptor table live?
Default is DRAM .bss (safest, no linker mods). For code that must allocate while the flash cache is off, choose IRAM .iram0.text (no patch, but the table is in the binary) or IRAM .iram0.bss (smaller binary, but requires patching esp8266.project.ld.in to add the *(.iram0.bss .iram0.bss.*) wildcard).
Will this work on ESP32?
No. The memory map (_bss_end, _iram_end, 0x40000000), the locking primitive and the heap API are ESP8266-specific by design.
About

Compact descriptor-based memory allocator for ESP8266 RTOS SDK. Zero in-band overhead, size-class DRAM regions, IRAM-first routing for MALLOC_CAP_32BIT, opt-in cross-region last resort, EXEC support, configurable descriptor placement (DRAM/IRAM .text/IRAM .bss), compact type widths, selectable diagnostics verbosity, configurable IRAM hot path scope. Drop-in replacement via linker --wrap.
