# MXR-MALLOC — проверка 30 замечаний

## Объект и границы проверки

- Проект: [Dzantemir/MXR-MALLOC, коммит `8df0101875e38628bd2d3bb9a195044e8f383856`](https://github.com/Dzantemir/MXR-MALLOC/tree/8df0101875e38628bd2d3bb9a195044e8f383856).

- Проверка исходников и небольшие тесты GCC на хосте. Полной Xtensa/IDF-сборки, дизассемблирования прошивки, измерения IRQ latency и запуска на ESP8266 не было. `xtensa-lx106-elf-gcc` в окружении не найден.
- Номера строк ниже относятся к зафиксированному коммиту; в исходном списке многие номера не совпадают с фактическими.
- Исходники проекта не изменялись. Локальная копия: `mxr-review/`. Проверочные примеры: `audit-check/`.

## Основной вывод

Исходный список содержит полезные находки, но не является надёжной классификацией «30 ошибок». Особенно неверно объявлять пункты 1–6 шестью доказанными критическими дефектами: часть утверждений противоречит самому ESP8266 RTOS SDK, часть требует машинного кода и измерений.

Воспроизведены на изолированном коде: превышение лимита IRAM при anti-sliver (#9), отсутствие заявленного early-exit в DRAM cross-region (#16), переполнение runtime-парсера (#17). Кроме того, обнаружена ошибка сборочной конфигурации, которую пункт #21 не распознал: IRAM-динамика без DRAM-динамики использует неопределённые макросы.

## 1. `#ifndef MALLOC_CAP_EXEC` против enum

**Вердикт: не подтверждается для проверенного SDK.**

В `components/heap/include/esp_heap_caps.h:34–39` SDK это именно `#define`, а не `enum malloc_cap_t`. Определения в `mxr_malloc/include/mxr_malloc.h:426–444` совпадают с SDK.

Два минимальных TU с настоящим заголовком SDK проверены через `gcc -Werror -fsyntax-only`: сначала `mxr_malloc.h`, затем `esp_heap_caps.h`, и в обратном порядке. Оба проходят.

Общий совет, что препроцессор не видит enum-константы, верен, но к показанному SDK он не доказывает ошибку. Для другого форка с enum нужна отдельная проверка.

## 2. Жёстко заданные границы арен

**Вердикт: не подтверждается как ошибка штатной конфигурации ESP8266 RTOS SDK.**

В MXR: `mxr_malloc.c:2916–2924,4257–4262`. В SDK `components/heap/port/esp8266/esp_heap_init.c:39–55` используются те же `_bss_end`, `_iram_end`, `0x40000000`, `0x40100000 + CONFIG_SOC_IRAM_SIZE`.

SDK `components/esp8266/ld/esp8266.ld:38` задаёт DRAM как `org=0x3FFE8000, len=0x18000`, то есть верх действительно `0x40000000`. Утверждение о захвате системного стека именно из-за этого адреса не доказано.

Для нестандартной карты памяти linker-symbol лучше числовой константы, но в MXR уже есть weak-функции `mxr_dram_arena_bounds` и `mxr_iram_arena_bounds`, которые приложение может переопределить. Это вопрос переносимости, не доказанное повреждение RAM.

## 3. Не подключён linker template

**Вердикт: частично подтверждается; реальный интеграционный риск, но причина описана неточно.**

CMake действительно не подключает `mxr_malloc/ld/esp8266.project.ld.in`. Однако README:466 и Kconfig:88–97 прямо предупреждают о необходимости патча для `MXR_DESC_IN_IRAM_BSS`. Это поставляемый шаблон для ручной интеграции, а не автоматически применяемый фрагмент.

У SDK уже есть выходная секция `.iram0.bss`, символы её начала/конца и обнуление в startup. Поэтому фраза «в SDK секции нет» неверна для проверенного SDK.

Существенное отличие шаблона MXR: явное включение `*(.iram0.bss .iram0.bss.*)` и `NOLOAD`. Стандартные linker mappings SDK не дают явного правила для этих входных секций MXR. Без патча полагаться на размещение orphan-секций опасно: надо проверить map-файл, положение данных относительно `_iram_end` и диапазон startup-обнуления. Само отсутствие патча не доказывает конкретный исход «состояние потеряется».

Рекомендация: автоматизировать mapping либо проверяемую интеграцию; предупреждение CMake полезно, но не заменяет правильный linker script. Просто добавить второй полный project script через `-T` — не универсальное исправление.

## 4. Обычный malloc запрашивает `MALLOC_CAP_32BIT`

**Вердикт: факт верен, но это не доказанное нарушение контракта именно ESP8266 RTOS SDK.**

MXR действительно допускает IRAM fallback для этих запросов. Это также прямо документировано в Kconfig:315–329, включая `malloc()`.

Но SDK `esp_heap_caps.h:121` сам описывает `malloc(s)` как `heap_caps_malloc(s, MALLOC_CAP_32BIT)`. Штатный IRAM heap имеет `MALLOC_CAP_32BIT | MALLOC_CAP_EXEC`. `MALLOC_CAP_DEFAULT`, на который ссылается аудит, в проверенном заголовке вообще отсутствует.

В SDK `components/freertos/port/esp8266/xtensa_vectors.S` есть `LoadStoreErrorHandler`, эмулирующий `l8ui/l16ui/l16si/s8i/s16i`. Поэтому обычные byte/halfword-обращения могут работать через исключения; «попал в IRAM — обязательно упал» неверно. Эмуляция дорогая и не означает поддержку любых инструкций/невыровненных доступов.

Если требуется гарантированно байтно-доступный пул без такой эмуляции, правильно запрашивать `MALLOC_CAP_8BIT | MALLOC_CAP_32BIT` или отключить data fallback. Но глобальную замену всех malloc-wrapper'ов надо оформлять как выбранную политику DRAM-only, а не как бесспорное исправление несовместимости SDK.

## 5. Free heap queries включают IRAM

**Вердикт: не подтверждается как несовместимость SDK.**

В `mxr_heap_wrap.c:130–138` действительно `MALLOC_CAP_32BIT`. Однако SDK `components/esp8266/source/system_api.c:378–388` реализует `esp_get_free_heap_size` и `esp_get_minimum_free_heap_size` точно через эту маску.

Эти функции не обещают именно DRAM-only. Для байтно-доступной памяти нужен отдельный запрос с `8BIT`, либо DRAM-query. Сценарий, что lwIP из-за этого обязательно получит OOM, в исходном аудите не прослежен по коду потребителя.

Если сознательно менять обычный malloc на DRAM-only, стоит отдельно решить, менять ли общие queries вместе с ним; это не следует автоматически из названия `free_heap_size`.

## 6. `*status = s_stats` и bytewise memcpy

**Вердикт: потенциальный IRAM-risk, но заявленная реализация и число исключений не доказаны.**

Присваивание есть: `mxr_malloc.c:4539`. C не гарантирует ни пословную копию, ни побайтовую; конкретный GCC может использовать инструкции словной копии или вызов `memcpy`. В SDK есть ROM-привязка `memcpy`, поэтому одного имени функции тоже недостаточно для вывода о ширине доступа.

Дополнительно исходный аудит смешал варианты структуры:

- На 32-битной ABI с состоянием в DRAM `sizeof(mxr_status_t) == 184`.
- С состоянием в IRAM, где поля расширены, `sizeof(mxr_status_t) == 204`.

Оба размера проверены `gcc -m32 -ffreestanding -fsyntax-only` через `_Static_assert`. Поэтому утверждение «184 входа в обработчик в IRAM-режиме» недостоверно сразу по двум причинам.

Явная word-copy разумна, но и `mxr_memcpy4` надо проверить в целевой дизассемблированной сборке: оптимизатор способен преобразовывать циклы в библиотечные операции. `sizeof` кратный четырём — необходимое, но не достаточное доказательство безопасного машинного кода.

## 7. Атрибуты `mxr_memset4/mxr_memcpy4/mxr_memmove4`

**Вердикт: подтверждается как условный дефект размещения кода.**

`mxr_malloc.c:171–207`: используется `MXR_IRAM_ALLOC_ATTR`. При CORE-only этот атрибут пуст, но helpers доступны из IRAM core-путей, например сдвигов таблиц:279,285,576,582.

`inline` не гарантирует встраивания. Out-of-line реализация без IRAM-атрибута может остаться во flash. Исправление на core IRAM-атрибут обосновано; окончательную cache-off safety проверять по map/disassembly и всему графу вызовов. Нельзя утверждать, что конкретная текущая release-сборка уже падает, не посмотрев её ELF.

## 8. Логирование из IRAM с flash-строками

**Вердикт: подтверждается как риск при отключённом flash cache.**

`mxr_canary_report` и `mxr_dfd_classify`: `mxr_malloc.c:1392–1402,1451–1463`. IRAM-атрибут функции не переносит во внутреннюю RAM строки формата, TAG и строки `IRAM`/`DRAM`. По стандартному mapping обычная `.rodata` компонента идёт во flash.

В SDK `ESP_EARLY_LOGE` вызывает `esp_early_log_write`; сама реализация раннего лога размещена в IRAM, а `log/linker.lf` задаёт `noflash_data` для библиотеки log. Это не переносит строки вызывающего компонента MXR.

Рекомендация: DRAM-размещение всех необходимых строк/данных и проверенный cache-safe logger либо только счётчики с отложенным выводом. Предложение «ROM-расположенные строки» некорректно как обычный способ добавления пользовательских строк: mask ROM чипа не переписывается. Одна замена макроса на `ets_printf` flash-строки не исправляет.

## 9. Anti-sliver превышает IRAM fallback limit

**Вердикт: подтверждено, воспроизведено на изолированном helper.**

В `mxr_iram_fb_find_free_in_region` и `mxr_iram_fb_find_free_and_largest` расширение проверяет `max_bytes` региона, но не `CONFIG_MXR_IRAM_FALLBACK_MAX_BYTES`. Общая проверка перед поиском проверяет исходный запрос, не итоговое расширение. In-place realloc отдельно проверяет итоговый размер:3923–3924.

Контрпример: limit=100, запрос=100, свободный gap=104, anti-sliver threshold=8, регион без верхнего лимита. Helper возвращает alloc_bytes=104. Это не переполнение буфера, а нарушение ограничения на размер fallback-блока.

Нужно ограничивать итоговый размер расширения и в обычном поиске, и в cross-region helper; если расширение запрещено, выделять исходные 100 байт, оставляя остаток.

## 10. Нет COMPAT-warning в CMake

**Вердикт: подтверждается как недоработка диагностики, не самостоятельная ошибка линковки.**

PORT предупреждается, COMPAT — нет. Фактические duplicate symbols зависят от того, какие объекты/архивы SDK включены и извлечены линкером. Предупреждение или проверка конфигурации полезны, но отсутствие warning само по себе не ломает код.

## 11. Число регионов задано PRIVATE

**Вердикт: подтверждается как проблема публичных конфигурационных макросов, не текущая ABI-поломка.**

`CMakeLists.txt:129–130` и аналогичные IRAM-ветки задают `MXR_PARSED_REGION_COUNT`/`MXR_IRAM_FB_PARSED_REGION_COUNT` только библиотеке. Потребитель публичного заголовка видит fallback=1 и может неверно интерпретировать эти макросы.

Публичные структуры сейчас от числа регионов не зависят. Для распространения согласованного значения нужен `PUBLIC` либо generated public config header. Простая замена PRIVATE на INTERFACE недостаточна: INTERFACE передаёт определения потребителям, но не собственной компиляции компонента.

## 12. MINIMAL dump всё равно сканирует

**Вердикт: лишняя работа подтверждается; обещание вывода не нарушено.**

`mxr_dump`:4916–4935 вне NORMAL/FULL получает глобальные и региональные snapshots, хотя региональная детализация затем не печатается. `dram_base/dram_total/dram_free/dram_min_free` и аналогичные IRAM-переменные не используются в MINIMAL; возможны set-but-unused warnings.

Однако Kconfig обещает «Print only ... totals», причём среди них есть `largest free block`. Он не обещает O(1) или отсутствие сканов. Для largest нужен поиск, если нет пригодного точного кэша. Убирать стоит лишние региональные snapshots и метрики фрагментации, но не считать всякий проход в MINIMAL нарушением контракта.

## 13. Инкременты realloc вне lock

**Вердикт: подтверждается.**

`mxr_malloc.c:3641–3652`: две ветки отказа до вызова `mxr_lock()` обновляют `s_stats.alloc_fail_no_memory`. Даже на одноядерном ESP8266 read-modify-write может быть прерван другим путём, меняющим счётчик. Это потеря статистики, а не доказанное повреждение allocator metadata.

Рекомендация: короткий lock вокруг обновления или общий безопасный helper счётчика.

## 14. Длинные IRQ-off участки

**Вердикт: структура критических участков подтверждается; последствия и микросекунды не измерены.**

`mxr_get_status`:5162–5169 держит lock во время `mxr_collect_status_locked`; тот сканирует largest, затем отдельно gaps/fragmentation. `mxr_dump` делает дополнительный сбор по регионам. Realloc move копирует данные до unlock; free/shrink может двигать таблицу под тем же lock.

Есть основания оптимизировать и измерять worst-case latency. Но «256 дескрипторов = десятки микросекунд = опасно для WiFi» без частоты CPU, конфигурации, размещения и аппаратного измерения — не установленный результат.

Нельзя просто вынести копию realloc за lock: сначала нужно доказать корректность времени жизни старого/нового блока и семантику доступа к таблицам.

## 15. Двойной поиск в IRAM fallback

**Вердикт: подтверждается как избыточный проход в части неудачных поисков.**

`mxr_try_iram_fallback`:3213–3219 после неуспеха поиска повторно вызывает `mxr_iram_fb_region_largest_free`. Не каждый отказ означает два полных прохода: есть быстрые проверки free/cache. Но при фрагментированном регионе без подходящего gap повторный проход реален.

Уместно возвращать largest вместе с результатом поиска и отмечать, точен ли он при раннем выходе.

## 16. DRAM cross-region early-exit не работает

**Вердикт: подтверждено по коду и изолированному тесту.**

`mxr_find_free_and_largest`:1883–1997 продолжает поиск ради largest. Условие «достаточно хороший gap» не фиксирует выбранный блок; дальнейшие gaps способны его заменить. Для выбора получается обычный best-fit. `best_fit_early_exits` здесь не растёт.

Тест: запрос 100, первый gap=108 укладывается в waste_limit=12; более поздний gap=100 всё равно заменяет его. Это рассогласование политики/метрик, не повреждение памяти. Сам полный проход объясним необходимостью точного largest; чтобы действительно экономить время, нужен контракт largest_exact либо иной кэш.

## 17. Переполнение decimal parser

**Вердикт: подтверждено, воспроизведено.**

`mxr_parse_region_config`:4156–4165 делает умножение и сложение до проверки верхней границы. Строка `4294967300-50%` на реальном извлечённом коде парсится как `min_bytes=4, percent=50` из-за uint32 wraparound.

Проверять до операции: `min_b > (0x7FFFFFFFu - digit) / 10u`. Это runtime-конфигурационный дефект, а не автоматически удалённо эксплуатируемая уязвимость. Обычная CMake-валидация ограничивает практическую достижимость.

## 18. `MIN_SLICE_BYTES=4`

**Вердикт: математически верно, но не обязательно ошибка.**

Положительный остаток кратен четырём, поэтому `waste < 4` невозможен. Порог 4 отключает именно расширения малых положительных остатков. Такая граничная настройка допустима; отдельный switch anti-sliver уже существует, поэтому можно улучшить UX: range 8–64 или явная справка. Это не аварийный дефект.

## 19. Отрицательный `BIG_GAP_MIN`

**Вердикт: подтверждается как недостающая валидация.**

Kconfig:986–992 не задаёт range; `mxr_malloc.c:961–962` явно приводит порог к uint32_t. Отрицательная настройка превращается в огромное положительное значение и меняет политику BGG. Нужен неотрицательный range и, для ручных сборок, compile-time guard.

## 20. INIT не связан с MAX_DESC

**Вердикт: описанный сценарий не доказывает ошибку.**

Если пользователь установил MAX_DESC=1, один дескриптор — именно заданный предел, и таблица не должна расти выше него. Clamp INIT к MAX в заголовке разумен. Можно согласовать диапазоны/подсказки Kconfig, но «навсегда одноэлементная» при ceiling=1 — ожидаемо.

Это не означает, что вся grow/shrink-логика доказана корректной: исходное широкое заверение аудита отдельно не принимается.

## 21. Зависимости IRAM dynamic — здесь реальная ошибка серьёзнее

**Вердикт: предлагаемая в списке «симметрия» не является точным исправлением. Найдена ошибка конфигурации сборки.**

`CONFIG_MXR_IRAM_DESC_DYNAMIC=y` разрешён при `CONFIG_MXR_DESC_DYNAMIC=n`. Но `MXR_DESC_INIT` и `MXR_DESC_CHUNK` объявлены внутри `#ifdef CONFIG_MXR_DESC_DYNAMIC` (`mxr_malloc.h:230–242`). IRAM-код безусловно использует их при своей динамике: `mxr_malloc.c:1614,1680–1695,2968–2976`.

Минимальный TU, включающий настоящий заголовок с USE_IRAM=y, IRAM_FALLBACK_ENABLED=y, IRAM_DESC_DYNAMIC=y и без DESC_DYNAMIC, даёт GCC:

```
error: 'MXR_DESC_INIT' undeclared
error: 'MXR_DESC_CHUNK' undeclared
```

Это допустимая через Kconfig комбинация, которая не может нормально скомпилироваться. Она ломается и без размещения статических таблиц в IRAM, поэтому один запрет `!MXR_DESC_IN_IRAM_TEXT && !MXR_DESC_IN_IRAM_BSS` не решает проблему.

Правильное направление: общие INIT/CHUNK определять при любой из двух динамик, а настройки Kconfig делать доступными при `MXR_DESC_DYNAMIC || MXR_IRAM_DESC_DYNAMIC`; начальные ёмкости лучше независимо ограничить DRAM/IRAM максимумами. Само статическое размещение DRAM-таблицы в IRAM не доказывает необходимость запрещать отдельную динамическую IRAM-таблицу.

## 22. Неиспользуемые hints в fallback-регионах

**Вердикт: подтверждается условно, объём в списке упрощён.**

Общий `mxr_region_t` действительно содержит DRAM hints и используется для fallback-регионов. При выключенном quick-fit этих полей нет; при обычном hint это 8 байт на регион; при binning — два массива, то есть `8 * MXR_BIN_COUNT` байт на регион.

Это footprint/поддерживаемость, не нарушение корректности. Разделять типы стоит, если выигрыш оправдывает усложнение.

## 23. Неиспользуемые includes

**Вердикт: подтверждается по прямым обращениям.**

В перечисленных исходниках нет прямых вызовов libc memory/string/stdio-функций. Удаление необязательных include допустимо после проверки реальных SDK-макросов и сборки. Приоритет низкий.

## 24. `MXR_OFF_FLAGS_MASK` не используется

**Вердикт: подтверждается.**

Единственное вхождение в исходниках компонента — определение `mxr_malloc.h:351`. Это косметика/резерв публичного API, не функциональная ошибка.

## 25. Дублирование IRAM-атрибутов

**Вердикт: подтверждается как замечание к поддерживаемости.**

Три похожих блока существуют. Централизация полезна, но публичный заголовок должен корректно работать и в host-тестах без `esp_attr.h`; не следует менять порядок include/атрибуты без проверки всех режимов.

## 26. Компенсация free при неизвестном регионе

**Вердикт: локальная несогласованность подтверждается, нормальный достижимый сценарий не показан.**

`mxr_free_locked`:3488–3500 обновляет глобальные free counters, но не free counters региона. `mxr_collect_status_locked` затем заново суммирует регионы, теряя такую коррекцию в `s_stats.free_bytes`.

Это путь уже нарушенного инварианта «валидный дескриптор принадлежит региону». Добавить компенсатор недостаточно для восстановления метаданных. Разумнее диагностировать первопричину, определить fail-safe поведение и не заявлять, что одна коррекция счётчика восстановила heap.

## 27. PORT-функции без прототипов

**Вердикт: подтверждено host-компилятором, но пояснение про zalloc в списке неверно.**

`gcc -Wmissing-prototypes -fsyntax-only` на `mxr_heap_port.c` сообщает пять предупреждений: malloc/free/calloc/realloc/zalloc. Для libc-функций нужен `<stdlib.h>`, для zalloc — подходящий SDK-прототип или собственное согласованное объявление.

В `mxr_malloc.h` объявлены `mxr_zalloc`, `mxr_zalloc_caps`, `_heap_caps_zalloc`, но не `zalloc`. Поэтому заявленного в аудите конфликта именно с объявлением `zalloc` в этом заголовке нет.

## 28. Сигнатура `_heap_caps_malloc`

**Вердикт: совпадает с проверенным SDK, текущая ошибка не подтверждается.**

SDK `esp_heap_caps.h:130`: `void *_heap_caps_malloc(size_t size, uint32_t caps, const char *file, size_t line);`. MXR использует ту же сигнатуру. Совместное включение заголовков проходит тест.

Поддержку других версий/форков стоит явно фиксировать и проверять. Общее «в разных версиях бывает иначе» не доказательство ошибки данного проекта с выбранным SDK.

## 29. Единственный регион `4-50%` становится плоским

**Вердикт: поведение есть, но это не ошибка процента в показанном примере.**

`mxr_init_regions_kconfig`:4220–4223 действительно выбирает flat region при одной записи. Однако CMake явно объявляет правило: нераспределённый остаток идёт последнему региону. При единственном `4-50%` он и есть последний: 50% + оставшиеся 50% = вся арена. Общая multi-region инициализация делает то же добавлением `remaining_bytes` последнему региону:4126–4131.

Отдельно можно ужесточить runtime validation для ручных сборок с неверной первой границей, но конкретный пример `4-50%` не демонстрирует ошибку.

## 30. Кодировки/переносы строк

**Вердикт: косметика; описание списка неточно.**

Побайтовая проверка:

- BOM присутствует не только в CMake, но также в `mxr_heap_compat.c`, `mxr_heap_port.c`, `mxr_heap_wrap.c`.
- Эти файлы используют LF.
- `ld/esp8266.project.ld.in` содержит CRLF: 258 строк.
- Значит, утверждение «все исходники UTF-8/LF» в отношении всего комплекта неверно.

Оснований считать это причиной поломки сборки нет.
